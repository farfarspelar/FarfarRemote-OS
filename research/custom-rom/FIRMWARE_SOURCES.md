# E2003 stock firmware and source research

## Target identity to match

Live device: E2003, Android 4.4.4/API 19, build `25.0.A.2.31`, Sony customization `1293-7358 R7A`. Firmware labels and region/revision matter. An E2003 image with different CDA is a candidate to inspect, not an automatically acceptable restore base. A new read-only property check on 2026-10-14 confirmed the customization specifically through `ro.semc.version.cust=1293-7358` and `ro.semc.version.cust_revision=R7A`; `ro.semc.version.sw=1292-0502` and `sw_variant=GENERICSS` are separate software-base fields and must not be mistaken for the customization ID.

### Flashtool E2003 profile verification — 2026-10-14

The public [Flashtool device database](https://github.com/Androxyde/devices) was cloned read-only and inspected at commit `4f354572579e62337d56a6b9319f7f8b31b3378a`. `E20XX/E20XX.properties` lists `E2003,E2033,E2053,E2006,E2043` and names the family “Sony Xperia E4g”; its flags are `canflash=true`, `canfastboot=true`, `cankernel=false`. The associated `default.fsc` includes `boot`, `fotakernel`, `system`, userdata and security-related operations. In Flashtool source commit `7529dce9a1ffb81e365ba1d7e15f6773463ffd7a`, `canRecovery()` is tied to a device-specific `bootkit` directory, rather than simply the profile's `canrecovery` text. This profile has no such folder in the database clone. The source confirms that “can flash” means enabling the Sony Flashmode firmware workflow; it is not evidence of a safe custom-recovery route.

This is a positive, model-specific tooling lead: Flashtool knows the E2003 identity and has an FSC recipe for the E4g family. It narrows uncertainty about selecting a host-side Sony firmware tool, but does not show that the current Linux install can complete a flash, authenticate any FTF, or restore this phone. The FSC includes partitions that must not be written casually. Use only as an offline format/profile finding; never select the R10A or another CDA package as an assumed restore. No phone was connected to Flashtool and no flashing operation was run.

### Boot and FOTA payload inspection

Only `boot.sin` and `fotakernel.sin` were extracted into `/tmp/farfar-e2003-sin-inspect`. Their SIN v3 MMCF/ADDR payload SHA-256 digests matched the hashes embedded in each file. Both decoded payloads are ARM ELF executables. ELF program headers show a first segment containing the same gzip-compressed kernel in both images and a second segment containing different gzip-compressed root filesystems. The first-segment decompressed bytes contain the kernel string `Linux version 3.10.48+ ... gcc 4.8 ... Tue Sep 8 11:03:22 CST 2015`.

The boot ramdisk's read-only cpio listing includes Android `init`, `init.mt6752.rc`, `fstab`, `adbd`, and Sony/MediaTek startup scripts. Its fstab mounts `/system` read-only and `/data`, `/cache`, `/protect1`, `/protect2`; the project init script creates MediaTek WMT/Wi-Fi/Bluetooth device nodes and starts connectivity services. Its `default.prop` says `ro.semc.version.sw=1292-0502`, `ro.semc.version.sw_variant=GENERICSS`, `ro.secure=1`, and `ro.debuggable=0`; this is not the live phone's `1293-7358 R7A` identity. This is evidence of the image's intended stack, not proof that this R10A image is interchangeable with the installed R7A image. The `fotakernel` ramdisk is a FOTA-oriented environment and is not validated as a usable recovery.

The SIN parser reference was the read-only v3 implementation in [Androxyde/Flashtool](https://github.com/Androxyde/Flashtool/tree/master/Flashtool/src/main/java/org/flashtool/parsers/sin/v3), checked out at commit `7529dce9a1ffb81e365ba1d7e15f6773463ffd7a`. The repository now includes `tools/extract_e2003_boot_payloads.py`, a bounded standard-library reader for only the two named SIN entries. It refuses non-E2003 manifests, requires a new output directory, verifies SHA-256 payload records and emits only 32-bit ARM ELF images. The general `j4nn/sinunpack` executable was not used because its main program scans all SINs and includes USB/flashing code. Extracted firmware and payloads remain outside the repository. Example: `python3 research/custom-rom/tools/extract_e2003_boot_payloads.py /absolute/path/to/E2003.ftf /tmp/e2003-boot-analysis`.

### Sony loader identity cross-check — 2026-10-14

The `loader.sin` ZIP entry was independently extracted in memory from the locally held E2003 R10A Customized UK and R3A Customized DE FTFs and hashed; both are byte-identical at 279,788 bytes, SHA-256 `3f9c2a29f35bbbc18139f34a09fae7238323ceb52ac2e098a06d5278c573b729`. The same hash was observed in duplicate local copies of the R3A archive. The payload contains the label `S1_Root_bee6`; community Flashtool logs for E2003 also report this loader family and the `S1_Boot_MT6732_TC9PRA_9` boot version ([example](https://4pda.to/forum/index.php?showtopic=668811&st=100)).

The loader contains an X.509 `S1_Root_bee6` certificate (SHA-256 fingerprint `405b75e329c951cc48f9d699fa2bc18c302233595affe5143ed2475160fac6e8`); the `boot.sin` header contains an `S1_SW` certificate issued by that root. Offline RSA/SHA-256 verification with Python `cryptography` 41.0.7 confirmed the root's self-signature and the `S1_SW` certificate signature under the embedded root public key. This verifies the **internal certificate signatures** in the candidate files. It still does not establish that this embedded root matches the immutable Sony Root CA key in this handset's Boot ROM, and it does not verify the SIN image signature over payload data. Sony describes its secure-boot chain as rooted in a Sony Root CA public key held in Boot ROM, with successive images verified before execution ([Sony security overview](https://www-support-downloads.sonymobile.com/support/XperiaInBusiness/Xperia_in_Business-Security-April_2016.pdf)). Therefore the FTFs remain third-party-hosted candidates, not authenticated Sony downloads or safe restore bases; their internal hashes establish file consistency only. They also do not prove restore/boot compatibility with the live CDA `1293-7358 R7A`. Proprietary bytes and extracted certificates remain outside Git.

Exact web searches for E2003 `1293-7358`, `1293-7358 R7A`, and `E2003 25.0.A.2.31 R7A` did not produce an exact package. One indexed `25.0.A.2.31 R7A Nextel PE` result is for **E2006**, and is not a valid substitute ([listing](https://azrom.net/rom-sony-xperia-e4g-e2003-e2006-e2053-ftf-firmware-lock-remove-file/)). A separate E2003 Customized MEA package is listed under CDA `1293-9486`, also not an exact match ([listing](https://xperiastockrom.com/sony-xperia-e4g-e2003/)). These are search leads only, not verified downloads or recovery bases.

### Kernel source search

The public Sony [`kernel-copyleft`](https://github.com/sonyxperiadev/kernel-copyleft) repository was checked through its current remote branch refs. It exposes older `14.1.*` and later Xperia kernel release branches, but no `25.0.A.*` branch or E2003/MT6752-specific source branch was found. Sony's current Open Devices device list likewise does not identify E2003. A public GitHub repository search performed on 2026-10-14 returned zero repositories for `callass android device tree`, `sony E2003 kernel`, `Xperia E4g ROM`, and `sony-mt6752 android device`. One related kernel repo surfaced: [`sony-mt6752/android_kernel_sony_mt6752-common`](https://github.com/sony-mt6752/android_kernel_sony_mt6752-common), whose description identifies Xperia C4/C5 Ultra; it is not an E2003 tree and is explicitly excluded as a build/flash source. This is a **bounded negative search**, not proof Sony never published a standalone archive elsewhere. A separate GitLab E2003 kernel mirror (documented at the start of this file and pinned to a commit) includes `callass` sources and compiled offline into a 3.10.48 ARM zImage, but its Sony provenance is unverified and the generated config has not been matched to live R7A. The extracted firmware kernel does not contain `IKCFG_ST`/`IKCFG_ED` markers for an embedded config.

An additional Sourcegraph search including archived and forked repositories found no indexed matches for `callass_defconfig`, `init.callass.rc`, or E2003 kernel-tree identifiers. This is corroborating negative evidence, not an exhaustive search of private or unindexed archives; it predates the GitLab mirror discovery. ## Extraction workflow (offline only)

1. Record where the FTF came from, exact URL/account/date, file size, archive listing and SHA-256. Do not place firmware/vendor binaries in public Git.
2. Run `research/custom-rom/tools/inspect_ftf.sh FILE.ftf [expected-sha256]`. This checks the ZIP container and lists entries; it does not flash or extract the archive.
3. Use an audited Sony SIN extractor/Flashtool version to extract image payloads to a separate local directory. Record tool version/hash and all output hashes. FTF is a Sony container (commonly ZIP with SIN files); not every SIN type is supported by every tool version.
4. Extract `kernel.sin`/boot payload and system image, then inspect boot metadata using a trusted host-side boot-image parser. Do not patch/repack until the stock image is understood.
5. Verify model/build/CDA by firmware metadata inside the package and compare with live device properties. Filename alone is not evidence.
6. Check whether extracted package includes `boot`, `fotakernel`, `system`, loader and any TA/security-critical data. Do not publish copyrighted images or vendor blobs.

Sony Companion software repair is a possible official recovery service but may choose current or server-available firmware and may wipe user data. It has not been tested on this E2003. Treat the only exact restore candidate as **BLOCKED** until a matching package and end-to-end recovery route are established.
